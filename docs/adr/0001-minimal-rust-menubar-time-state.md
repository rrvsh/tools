# ADR 0001: NixOS Hyprland Time-Window Bar

- Status: Proposed
- Date: 2026-02-21
- Scope: NixOS + Hyprland only

## Problem Statement

We need a simple menu bar behavior where:

- right side shows current time,
- left side shows a string selected by local time windows (for example, `X` from `07:00` to `09:00`, otherwise `Y`).

The solution should fit this repository's NixOS + Home Manager setup and keep logic easy to test.

## Repository Context

- Hyprland is configured in `nix/modules/hyprland.nix`.
- Host `nemesis` imports that module via `nix/configs/nemesis.nix`.
- No existing `waybar`/`eww`/AGS config was present when this ADR was written.

## Alternatives Considered

### Bar Surface

1. Waybar custom module
   - Pros: native Hyprland workflow, simple right/left layout, declarative in Home Manager.
   - Cons: introduces Waybar config.
2. Eww/AGS
   - Pros: flexible widgets.
   - Cons: extra complexity for a small use case.
3. Fully bespoke Rust layer-shell bar
   - Pros: maximal control.
   - Cons: highest implementation and maintenance cost.

Decision: choose Waybar.

### Logic Runtime

1. Rust CLI called by Waybar interval
   - Pros: typed, testable, tiny runtime surface.
   - Cons: polled execution.
2. Shell script
   - Pros: fastest prototype.
   - Cons: weaker typing and testability.
3. Long-running daemon + signal updates
   - Pros: precise updates.
   - Cons: more lifecycle and IPC complexity.

Decision: choose Rust CLI with interval polling first.

### Time Handling

1. `chrono`
   - Pros: straightforward local time formatting and date math.
   - Cons: broader API surface.
2. `time`
   - Pros: lean modern API.
   - Cons: slightly more plumbing for local-time ergonomics.
3. `std::time`
   - Pros: zero extra deps.
   - Cons: poor calendar/timezone ergonomics.

Decision: choose `chrono`.

### Configuration

1. TOML generated by Home Manager
   - Pros: declarative and editable without recompiling.
   - Cons: validation logic needed.
2. Compile-time constants
   - Pros: minimal code.
   - Cons: rebuild needed for every schedule change.
3. Environment variables
   - Pros: easy injection.
   - Cons: awkward for multiple windows.

Decision: choose TOML from Home Manager.

## Design

- Waybar owns presentation/layout.
- Rust binary outputs module text for left-side state.
- Waybar `clock` module renders right-side time.
- Rule semantics: inclusive start, exclusive end (`[start, end)`) with overnight wrap support.

Data model:

- `Rule { label, start_minute, end_minute }`
- `RuleSet { rules, fallback_label }`

## Implementation Plan

1. Enable Waybar in `nix/modules/hyprland.nix`.
2. Start with minimal bar (right clock only) to validate integration.
3. Add Rust CLI crate for time-window label output.
4. Add Waybar custom module calling the Rust binary at interval.
5. Wire TOML config generated by Home Manager.

## Testing

- Rust unit tests for boundary behavior (07:00, 09:00, overnight rules).
- Integration tests for config parsing and output format.
- Nix checks via `nix flake check`.
- Runtime verification in Hyprland session.

## Security and Performance

- Local-only processing, no network requirement.
- Validate config input strictly (`HH:MM` bounds, malformed rule rejection).
- Polling every 30-60 seconds is low overhead for this use case.
